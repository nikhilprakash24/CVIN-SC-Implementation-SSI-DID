## 1. The lineage, in one figure and five documents

The testbed did not start as a testbed. It started as a **two-stage sandbox** — a
"versatile base to build and test anything", with a generic Python stage (off-chain
logic, a placeholder for an LLM interface) and a Web3 DApp stage (on-chain
interaction), plus generic hooks for a database, a cloud service and an API "to
represent generically a call to read something like a credential or identity on- or
off-chain". The guide's own success image was a Swiss-army-knife base case able to
"test and ship … the 6 implementation variations of CVIN-ID".

Five documents then turned that base into a research instrument, in order:

| Document | Date | What it added | What it fixed as scope |
|---|---|---|---|
| `MOBI_VID_RESEARCH.md` | 2025-11-10 | The standards frame: MOBI VID I/II, W3C DID/VC, SSI principles; the ERC-1056-as-base architecture; a P0/P1/P2 requirements matrix | The identity *standard* the vehicle would carry |
| `MOBI_VID1_TECHNICAL_SPEC.md` | 2025-11-10 | The VID I contract (`registerVehicleBirth`, VIN hash + encrypted VIN, ownership history), the Python provider, the four-layer architecture, seven success criteria | The *first contract* and its measurable targets |
| `CV2X_REALISTIC_ROADMAP.md` | 2025-11-10 | Phases 4–8: SUMO, five safety scenarios, 100/200-vehicle scale, attack scenarios, hardware; twelve success criteria; five research questions with hypotheses | The *experimental programme* |
| `MOBI_VID2_SSI_DESIGN.md` | 2025-11-10 | VID II lifecycle events (10 types, 8 roles), the full SSI stack (issuer/holder/verifier), a W3C checklist scored at DID 60% / VC 0% / SSI 80%, the centralized control baseline, ten use cases | The *comparison design* and the VC layer |
| `CAPABILITIES.md` | 2026-06-21 | A capability-by-capability inventory with code snippets and estimated gas/latency; a capability matrix; "currently working / partial / planned" | The *claimed state* at mid-2026 |

The architecture figure (`review_architecture.png`) shows the four planned layers
becoming five on the trunk: the **W3C SSI layer** (VC issuer/holder/verifier, DID
resolver, MOBI VID Python) and the **identity-provider abstraction** (PKI, centralized,
ERC-1056, MOBI VID behind one `IdentityProvider` interface) are the two structural
additions the design documents did not foresee, and they are what made the
PKI-vs-ERC-1056 experiment a one-script job. The sandbox's LLM-interface stage was never
built and is not missed — see §5.8.

## 2. Plan versus actual, criterion by criterion

The criteria matrix (`review_criteria_matrix.png`) scores every success criterion the
three design documents wrote down. Totals: **13 met · 9 partial · 1 open · 2 dropped**
of 25 (the figure computes these from the same table; an earlier draft of this
sentence said 11/11 before two statuses were corrected for the harness facts). The pattern behind the numbers:

**What the roadmap got right and the trunk delivers.** Identity systems, the CV2X
stack with a PKI provider, and the comparison framework (Phases 1–3) are complete and
verified. Sybil resistance via manufacturer-authorised birth registration is
implemented and exercised by the 68-scenario security harness across all nine
standards. Replay is prevented by challenge/domain binding in the VC layer and
timestamp checks in the BSM path. The "centralized vs MOBI VID gap" is now quantified
(claim register #21). The cost analysis exists as the nine-standard gas table (#25).

**What was delivered at a different layer than planned.** The roadmap's Phase 5
"safety-critical scenarios" became the twelve lifecycle use cases — richer in identity
terms, but not SUMO scenarios with FCW/EEBL/IMA logic and a measured decision path.
Phase 7's attack scenarios were realised as a **contract-level** harness (Hardhat, 68
`it` blocks) plus harness-level `run_attack_tests`, not as SUMO-level attacks with
mobility. Both are legitimate substitutions for a MASc; both must be *described* as
substitutions in chapter 3.

**The SUMO nuance.** "SUMO integration with 50 vehicles" reads as unmet until one
opens `cv2x-testbed/sumo/results/`: the harness has been run — 50 vehicles (35 SSI, 15
PKI), 10 Hz BSMs, 300 m neighbour radius, 30 seeds, sign/verify cold and warm — but in
`--simulate` mode, which uses `MockMobility` rather than SUMO's TraCI. The *identity*
measurements are real; the *mobility* is synthetic. This is exactly the kind of fact
that should be stated in one sentence in the results chapter rather than left for an
examiner to find in a JSON header. The real TraCI mode exists in the same script and
has never been run because no SUMO binary was available in any session (§ plan).

**Two quiet drops, now recorded.** Position-falsification detection (>95%) and the
privacy analysis left the scope without a decision record; both are logged as SC-01
and SC-02. §5.2 below proposes a bounded way to bring the first back.

**Number drift the design documents contain, and its status now.** The documents carry
estimates that later measurement contradicts, and the trunk's claim register now labels
each: DID creation "~45,000 gas" (measured 52,594 bare / 78,068 with VIN — #7); NFT
minting "~150,000" (bare mint 102,804; VIN-bound `mintVehicle` 542,378 — #8); "DID
resolution 50–100 ms with blockchain lookup" (never measured; in-process 0.009 ms —
#10); "throughput ~15 TPS (Ethereum)", "$5 registration", "$640/MB on-chain" (design
estimates with no source; #20 covers fiat conversion — the throughput and storage
figures should be sourced or removed). The roadmap's RQ1 hypothesis — "10–100× slower
for writes, similar for reads" — is answered with more structure than it asked for:
on a local node, *register* is ≈1× (16.9 vs 15.2 ms), *issue* is 19×, and the hot-path
*verify* is 57× **only if** the chain is read at message time; off-chain verification
is PKI-class. The hypothesis was about the wrong axis: what matters is not read vs
write but *on the hot path vs off it*.

**Where the design overshot and the trunk quietly corrected it.** The VID II design
planned 10 event types and 8 roles; the contract has 11 and 9 (`REGISTRATION` and
`DECOMMISSION` added, `DEALER` added). The design planned 10 use cases; the trunk has 12
(dealership-mediated sale, end-of-life decommission). The compliance checklist was
scored 60/0/80 in the design; the trunk's internal instrument reports 93.2% on an
executable basis and the external W3C suite 74.4% with a precise failure list. Each
of these is an improvement; none is recorded as a change anywhere but here and
`SCOPE_CHANGES.md`.

## 3. Drift the review found that the audit had not

1. **The sandbox's "generic API/DB/cloud hooks" idea survives as the provider
   abstraction** — but the design documents never say so. The thesis should credit the
   sandbox guide as the origin of the `IdentityProvider` interface; it is the single
   most reused design decision in the codebase.
2. **The MOBI VID I spec's three-tier VIN privacy** (hash on-chain, encrypted
   off-chain, ZK proof of ownership) is two-thirds built: the VIN cipher tests exist,
   the ZK tier does not and is never mentioned again. Record as future work (SC entry
   pending) rather than let a reader assume it exists.
3. **The centralized baseline was designed for "fair comparison"** (feature parity:
   birth, lifecycle, ownership, multi-party issuance) and exists
   (`centralized_vehicle_registry.py`), but the PKI-vs-ERC-1056 experiment compares
   against the *IEEE 1609.2-style PKI provider*, not this registry, for the lifecycle
   operations. The register's #21 says "pki_centralized" for the fast column; the
   lifecycle-parity comparison the VID II design asked for has not been run.
4. **The roadmap's RQ5 (trust, user study)** is correctly marked future work in the
   roadmap itself; the README's contribution list still implies policy insight. Fine
   as long as chapter 7 owns it.

## 4. Grounding: twelve canonical or closely related works, and what this project did with each

Each entry: (i) what the work is and why it is canonical or close; (ii) how it was or
was not incorporated, with the repository evidence. Sources were verified by web
search on 2026-09-25; where a detail could not be verified it is marked.

### 4.1 SAE J2945/1 — On-Board System Requirements for V2V Safety Communications
(i) The normative source for the BSM cadence (10 Hz, 100 ms inter-message interval)
and for the timing envelope of V2V safety applications; every latency claim in the
V2X literature is ultimately measured against it. It also fixes what a BSM carries
and how security headers (IEEE 1609.2) ride along.
(ii) **Incorporated late and now explicitly.** The roadmap used "<10 ms verification"
and "<100 ms end-to-end" as targets without deriving them; `docs/LATENCY_BUDGET.md`
now derives the identity budget from J2945/1's cadence and computes neighbour
saturation P*(f) from measured data. The SUMO harness already runs BSMs at 10 Hz
(`bsm_rate_hz: 10` in the results header), so the cadence was built in from the start
even if the citation was not. — https://saemobilus.sae.org/content/j2945/1_201603

### 4.2 Brecht et al. 2018 — "A Security Credential Management System for V2X Communications" (IEEE T-ITS 19(12))
(i) The canonical description of the SCMS: bootstrapping, pseudonym-certificate
provisioning split across organisations for privacy (butterfly keys), misbehaviour
reporting, and revocation — the deployed North American PKI baseline that any
"alternative to PKI" claim must be measured against.
(ii) **Partially incorporated, as the PKI provider's model.** `pki_identity.py`
implements the SCMS *shape* — CA, enrolment certificate, a pool of ~20 pseudonym
certificates with 5-minute rotation, a CRL — and the PKI-vs-ERC-1056 experiment issues
21 certificates per registration to mirror it. What is not incorporated: the
multi-organisation split (RA/PCA/LA), OCSP/CRL distribution latency, and the linkage
values that make revocation of a pseudonym pool efficient. The register's caveat that
the in-process PKI is a *lower bound* on deployed PKI is exactly this gap. The thesis
should cite Brecht et al. when describing the baseline and name the three omissions.
— https://dl.acm.org/doi/10.1109/TITS.2018.2797529

### 4.3 Sommer, German, Dressler 2011 — Veins: "Bidirectionally Coupled Network and Road Traffic Simulation for Improved IVC Analysis" (IEEE TMC 10(1))
(i) The canonical vehicular co-simulation framework: OMNeT++ (network) and SUMO (road
traffic) coupled bidirectionally so that communication affects driving and driving
affects communication. Most V2X simulation papers since 2011 either use Veins or
justify why not.
(ii) **Not incorporated; the harness is single-domain.** `sumo_identity_integration.py`
couples identity logic to SUMO via TraCI (or to `MockMobility`) but has no network
simulator: messages are delivered to every neighbour within 300 m, capped at 8
receivers per broadcast, with no channel model. This is a deliberate, defensible
simplification for an identity thesis — the quantity of interest is the identity
pipeline's cost per received message, not packet loss — but it must be stated as
such, citing Veins as the framework whose fidelity was traded away and why. — https://veins.car2x.org/ ; https://www.semanticscholar.org/paper/1783fdfa44bcab6c9658988aa99b1b1d09308544

### 4.4 Eclipse MOSAIC (formerly VSimRTI)
(i) The open-source multi-domain co-simulation runtime that couples SUMO (via TraCI)
with OMNeT++/ns-3 or its own Simple Network Simulator, and with application models —
the contemporary "batteries-included" alternative to Veins for connected-automated
mobility studies.
(ii) **Not incorporated; a candidate for the SUMO plan.** MOSAIC's application layer
(Java "apps" attached to vehicles) is precisely where an identity-verification step
would sit, and its SNS would give the harness a channel model without OMNeT++'s
setup cost. `docs/PLAN_MOBI_SUMO.md` lists MOSAIC coupling as the third SUMO step,
after the existing TraCI mode is run for real. — https://eclipse.dev/mosaic/

### 4.5 van der Heijden, Lukaseder, Kargl 2018 — VeReMi: A Dataset for Comparable Evaluation of Misbehavior Detection in VANETs
(i) The reference misbehaviour dataset: labelled BSM logs from LuST + Veins with
injected position-falsification attacks, built so detection mechanisms can be compared
on the same data. It is the canonical answer to "how do you evaluate
position-falsification detection?".
(ii) **Not incorporated — and it is the cheapest way to revive SC-01.** The roadmap
dropped ">95% position-falsification detection" because detection is a separate
field. VeReMi turns that into a bounded experiment: replay VeReMi traces through the
identity layer and measure what identity *does* and *does not* catch. The honest
expected result — identity authenticates the sender and cannot see the lie in the
payload — is itself a chapter-6 point about the division of labour between identity
and misbehaviour detection, and it costs a day, not a field. — https://arxiv.org/abs/1804.06701

### 4.6 DIF `ethr-did-registry` / `ethr-did-resolver` — the did:ethr method specification
(i) The reference implementation of ERC-1056 as a DID method: the registry contract
and the resolver that rebuilds a DID document by walking `DIDAttributeChanged` /
`DIDDelegateChanged` events from `changed(identity)` backwards. Veramo and uPort ship
it; it is what "ERC-1056 identity" means in practice.
(ii) **Incorporated in structure, diverged in the resolver, now converging.** The
contracts follow the registry's API and event model. The trunk's own resolver
(`did_resolver.py`) for months returned a placeholder key and only on 2026-09-24 gained
a real `previousChange` event walk in the provider — i.e. the project re-derived what
`ethr-did-resolver` has done since 2018. The external W3C suite's 113 failures are all
resolution-metadata conformance the reference resolver handles. Recommendation: cite
the method spec as the normative reference, and either (a) adopt its metadata
conventions in `did_resolver.py`, or (b) run the reference resolver against the
project's registry as an *independent* conformance witness. — https://github.com/decentralized-identity/ethr-did-resolver/blob/master/doc/did-method-spec.md

### 4.7 Fdhila, Stifter, Kostal, Saglam, Sabadello 2021 — "Methods for Decentralized Identities: Evaluation and Insights" (BPM 2021 Blockchain Forum)
(i) The closest published *comparative* evaluation of DID methods, organised by the
W3C DID Method Rubric's categories; qualitative, method-level, not domain-constrained.
(ii) **Incorporated as the positioning anchor.** Audit 01 §4 and
`docs/DID_METHOD_RUBRIC.md` adopt the same rubric so the thesis's qualitative axis is
commensurable with Fdhila et al., and place the contribution on the *measured,
automotive-constrained* axis they do not have. Not yet incorporated: a side-by-side of
their did:ethr assessment against this project's ERC-1056 profile — a half-page table
for chapter 2. — https://eprint.iacr.org/2021/1087

### 4.8 W3C DID Method Rubric v2.0 (Group Note, 22 September 2026) and the W3C DID Test Suite
(i) The rubric is the community's evaluation vocabulary for DID methods (45 criteria,
seven groups); the test suite is the conformance instrument (46 implementations
submitted at DID 1.0 publication). Together they define "compared against the
standard" for this field.
(ii) **Both incorporated this session.** The rubric mapping exists with the
ledger-envelope finding (30 of 45 criteria are shared by all Ethereum registries); the
test suite was run against the project's resolver (328/441) with the failure classes
named. Not incorporated: the fixes the failures imply (five root causes) — scheduled in
the plan. — https://www.w3.org/TR/did-rubric/ ; https://github.com/w3c/did-test-suite

### 4.9 MOBI Vehicle Identity standards VID I (2019) and VID II (2021)
(i) The industry standards this thesis realises: VID I defines the vehicle birth
certificate as the immutable anchor tied to the VIN; VID II uses it for lifecycle
use cases, with vehicle registration and maintenance traceability as the working
group's two focus cases. Chaired by BMW and Ford (VID II) and Renault and Ford (VID I).
(ii) **Incorporated as the application profile, with one gap.** The contracts
implement VID I birth registration and VID II events (11 types, 9 roles, attestations),
and the five-backend sweep measures how faithfully each standard can carry them
(fidelity 3/5–5/5). The gap: the project's VID I/II requirement checklist was written
from secondary sources (announcements) and never reconciled clause-by-clause with the
standard text (the VID I preview PDF is linked in `MOBI_VID_RESEARCH.md`). Plan step
M1 does that reconciliation. — https://dlt.mobi/mobi-standards-for-deployment-of-vehicle-identity-vid-on-blockchain/

### 4.10 Kailus, Kern, Krauß 2024 — "Self-Sovereign Identity for Electric Vehicle Charging" (ACNS 2024; arXiv 2403.06632)
(i) The closest recent *engineering* paper: SSI credentials replacing the ISO 15118
Plug-and-Charge PKI, with an implementation shown to work with ISO 15118 and a formal
security/privacy analysis in the Tamarin prover.
(ii) **Not incorporated; two things to take.** First, it is the model for how a
vehicle-SSI paper argues security — a formal model, not a scenario list — and
suggests that the thesis's threat model (`docs/THREAT_MODEL.md`) could be strengthened
by a Tamarin model of the EIP-191 VC proof and the challenge/domain presentation.
Second, its framing (SSI *removes* a PKI's operational complexity) is the sharper
version of this thesis's "alternative to PKI" conjunct: the comparison is not only
latency and gas but *who has to run what*. — https://arxiv.org/abs/2403.06632

### 4.11 Lu, Wang, Qu, Zhang, Liu 2019 — "A Blockchain-Based Privacy-Preserving Authentication Scheme for VANETs" (IEEE T-VLSI 27(12); often mis-cited to T-VT)
(i) A widely cited blockchain-VANET authentication scheme (Merkle Patricia tree
anchoring, distributed authentication "within 1 ms" on the vehicle), representative
of the design-a-scheme-and-analyse-it genre this thesis positions itself against.
(ii) **Not incorporated; cite as the contrast.** Lu et al. propose *one* scheme and
report *one* latency; this thesis measures *nine* standards on one testbed under one
budget. The chapter-2 contrast should say so, and should use the correct venue —
IEEE Transactions on Very Large Scale Integration (VLSI) Systems, not Vehicular
Technology — since several secondary sources get it wrong. — https://www.semanticscholar.org/paper/1aae5f085ace33990a4b73b082b7bde91a34b553

### 4.12 EBSI — the European Blockchain Services Infrastructure's Verifiable Credentials framework and wallet conformance testing
(i) The largest public-sector deployment of W3C DIDs/VCs: a permissioned ledger, a
VC framework, OpenID4VC issuance/presentation, and a **wallet conformance test
service** third-party wallets must pass. It is the canonical example of *external*
conformance for the VC side, as the W3C test suite is for the DID side.
(ii) **Not incorporated; it answers audit F5's VC half.** The project's VC layer is
self-scored (VC DM 2.0, 27/29). EBSI's conformance approach — issue and present
through OpenID4VCI/OpenID4VP and pass an external checker — is the model for an
external VC witness. Even without joining EBSI, expressing one issuance and one
presentation in OpenID4VC form and validating them with an open conformance tool would
give the VC layer what the DID test suite gave the resolver. — https://hub.ebsi.eu/docs/foundations/verifiable-credentials/framework

### 4.13 BLOCKBENCH (Dinh et al., SIGMOD 2017) and the ACM SIGSOFT Empirical Standards
(i) BLOCKBENCH fixed the vocabulary for blockchain benchmarking (throughput, latency,
scalability, fault tolerance; macro- and micro-workloads); the SIGSOFT standards fix
what an empirical software-engineering study must report (workload, environment,
repetition, artifacts, threats to validity as design input).
(ii) **Incorporated as method discipline.** The claim register's rules (deterministic
gas → exact; latency → N, median, p95, environment header) and the CI drift check on
the gas benchmark follow both. Not incorporated: BLOCKBENCH's *throughput* dimension —
which is why SC-05 asks whether "throughput" stays in RQ1. — https://dl.acm.org/doi/10.1145/3035918.3064033 ; https://www2.sigsoft.org/EmpiricalStandards/

*(Also verified but not expanded here: Schäffner's master's thesis on SSI evaluation
and the 2025 Springer SSI-V2V authentication chapter — both used in Audit 01 §4.)*

## 5. Innovation opportunities the existing infrastructure makes cheap

Each is grounded in something already on the trunk and in one of the works above; each
names the experiment, not just the idea.

1. **Freshness-k cached verifier (from `LATENCY_BUDGET.md` §4).** Add a `k` parameter
   to the ERC-1056 provider: refresh key/revocation state from the chain every k
   messages. Sweep k ∈ {1, 5, 25, ∞} in `experiment_pki_vs_erc1056.py` and plot P*(0.5)
   against k with the analytic curve t_eff = 0.4 + 2.5/k ms. This turns H3 from a
   binary into a *design frontier* — the thesis's own contribution, not a re-statement
   of "on-chain is slow". One day.
2. **VeReMi replay through the identity layer (§4.5).** Feed VeReMi position-
   falsification traces through `SSIIdentityLayer.verify`; record that every forged
   *payload* passes authentication (expected) while every forged *sender* fails. Report
   as the division of labour between identity and misbehaviour detection; revive SC-01
   in this bounded form. One to two days.
3. **Run the TraCI mode that already exists.** Install `eclipse-sumo`, run
   `sumo_identity_integration.py` without `--simulate` on the existing
   highway-intersection network, 30 seeds, and compare with the mock-mobility results
   — the comparison itself is a validation of the mock. Half a day after install.
4. **Pseudonym pools on ERC-1056 as an SCMS analogue (§4.2).** SCMS privacy comes from
   ~20 rotating pseudonym certificates. ERC-1056 delegates with `validTo` are a native
   pseudonym mechanism: measure the gas and the linkability of a 20-delegate rotation
   scheme versus SCMS's butterfly keys. This is the privacy analysis SC-02 deferred,
   made concrete and measurable.
5. **Reference-resolver witness (§4.6).** Point `ethr-did-resolver` at the project's
   deployed registry and diff its DID document against `did_resolver.py`'s output. An
   independent implementation agreeing with yours is worth more than a checker you
   wrote.
6. **OpenID4VC conformance for the VC layer (§4.12).** One issuance and one
   presentation in OpenID4VCI/VP form, validated externally — the VC counterpart of the
   DID test-suite run.
7. **Tamarin model of the presentation protocol (§4.10).** Model challenge/domain
   binding and EIP-191 proofs; prove replay and impersonation resistance formally
   rather than by scenario. Reuse Kailus et al.'s modelling pattern.
8. **The sandbox's LLM interface, re-scoped as a demonstrator.** The 2025 sandbox
   guide imagined an LLM front-end. It is not a research contribution and should not be
   one; but a natural-language query over the vehicle's verifiable history ("show me
   every inspection since the last ownership transfer, with proofs") is a compelling
   *defence demo* of the VC layer's selective disclosure, buildable in a day from the
   existing holder wallet. Keep it out of the contribution list; keep it in the talk.
