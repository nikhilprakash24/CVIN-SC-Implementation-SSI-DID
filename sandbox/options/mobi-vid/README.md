# MOBI VID I + II — feature demos (plan S7)

**Identity model.** A vehicle is an ERC-1056 identity *address* (its own key) in a shared `MOBIVIDRegistryV2`; an authorised manufacturer anchors a VID I birth certificate to it — a VIN **hash**, an **encrypted** VIN, a certificate hash and the first owner, who becomes the ERC-1056 `owner` (only a pristine identity with no DID history can be born, K-4) — and from then on the owner manages delegates/attributes (event-only, ERC-1056 style), sells with odometer-stamped `transferVehicleOwnership` (the only controller change of a born vehicle since K-3), and role-authorised issuers (8 `IssuerRole`s) record 11 `EventType`s of VID II lifecycle events that other issuers can co-sign with on-chain-verified `attestEvent`. The Python provider adds the off-chain V2X hot path (`sign_message`/`verify_message`, SHA-256 + secp256k1 over raw digests).

Run one demo: `cd 1_blockchain-identity && npx hardhat run ../sandbox/options/mobi-vid/demos/<family>.js`. `demos/_lib.js` is the shared step printer. 276 steps, 78 mined transactions (deployment and `setup` steps not counted; the former `changeOwner` transactions on born vehicles are expected reverts since K-3, the clean-up ones on revoked identities since the D21 fix).

## Asymmetry notes

- **Creation: minted/registered.** The identity address is a key the vehicle (or the adapter, deterministically from the VIN) chooses off-chain; it becomes a vehicle only through the manufacturer's `registerVehicleBirth` (277 k gas in L1). Birth hands ERC-1056 control to `firstOwner`, so the vehicle's own key loses `owner` status at birth. The ERC-1056 `registerVehicle` path (self-registration by publishing a veriKey attribute) is disjoint from VID I and can be repeated; since K-4 an identity that has used it (or has any other DID history, `changed != 0`) can no longer be given a birth certificate.
- **Veracity and automation.** The chain enforces the manufacturer set, the owner on every ERC-1056 write, the 11×8 role matrix on `recordLifecycleEvent` (plus, since K-15, that an OWNER-role issuer is the vehicle's current `identityOwner`), existence/non-revocation checks, and — unique among the compared options — an **on-chain signature check** on `attestEvent` bound to (registry, chainId, vehicle, eventId). It stores event structs, counters, odometer series, ownership records and attestations, so history is queryable without logs. Since K-3 the public `changeOwner` reverts for a born vehicle, so every controller change goes through `transferVehicleOwnership` and the VID II ownership history is complete. It does not enforce odometer monotonicity, does not re-check issuer status on read, the OWNER role is still *granted* registry-wide (only its use is scoped by K-15), and a `DECOMMISSION` event does not set the revoked flag (the flag itself, since the D21 fix, is terminal and blocks every ERC-1056 mutator and `transferVehicleOwnership`). ERC-1056 delegates/attributes remain event-only (no getters, no `validDelegate`), so DID-document resolution is log replay.
- **Cryptography / hashing.** VIN privacy: `vinHash` is whatever bytes32 the caller supplies (provider: SHA-256 with salt; adapter: keccak256 — uniqueness therefore holds only per convention) plus an opaque encrypted VIN. `attestEvent`: `keccak256(abi.encodePacked(...))` under the **EIP-191** envelope, OZ `ECDSA.recover` (low-s enforced), must equal `msg.sender`; a raw-digest signature is rejected. Off-chain messaging (provider): SHA-256 of canonical JSON, secp256k1 ECDSA over the **raw digest** (no EIP-191, no chain id), verified against the key bound to the vehicle at registration (D11 fix: an embedded public key must equal the registered one; unknown and revoked vehicles are rejected). Since the D11b fix the provider anchors that key on-chain right after the birth (`anchorVehicleKey` → `DIDAttributeChanged` under `did/pub/secp256k1/veriKey/base64`, 100-year validity), and a verifier with no local record resolves it by walking `changed()` backwards from `lastChanged` — the same walk the ERC-1056 provider uses. Attribute names are bytes32 (`encodeBytes32String` or `keccak256`), event ids `keccak256(vehicle, type, issuer, timestamp, count)`.
- **Implemented but never compared.** All EventTypes except MAINTENANCE/REPAIR and all IssuerRoles except SERVICE_CENTER, the `verified` flag, multi-party attestations and their negative space, `getEventsByType`/`getOdometerHistory`/`getEventTypeCount`/`getVehicleEvents`/`getEvent`, raw getters, `changeOwner` on a bare identity vs `transferVehicleOwnership` on a born one, `updateVehicleKey`, `revokeAttribute`/`revokeDelegate`, `birthAttributes`, manufacturer/issuer/authority administration, `getVehicleDID`/`getVehicleInfo`, VIN decryption, and the entire off-chain hot path.

## Coverage check

Union of functions exercised across the eleven demos vs the public/external ABI: **MOBIVIDRegistryV2 57/57 (which includes the full MOBIVIDRegistry and ERC1056Registry surface; +3 with the D11b `anchorVehicleKey`, `vehicleKeyAnchored`, `VEHICLE_KEY_ATTRIBUTE`; K-3, K-4 and K-15 changed behaviour, not the ABI) — no uncovered function** (`revoked` appears only in the combined label `isRevoked+revoked+revokedAt` of `revocation.js`). Provider-only methods (`sign_message`, `verify_message`, `export_vin_key`, `*_credential`, `resolve_identity`) are mirrored, not executed, because they are Python.

Behaviour worth flagging. *Fixed 2026-10-04 (see `docs/DEFECT_LOG.md`; the demos assert the fixed behaviour and mark the steps `FIXED (Dnn)`):* D10 — `getVehicleDID` now returns `did:ethr:0x<chainId>:0x<40 hex>` (conformant; `did-resolution.js` asserts the shape); D11 — the provider's `verify_message` binds to the registered key, so an impostor embedding its own key under the vehicle's DID is rejected; D11b — the vehicle key is anchored on-chain at registration (`anchorVehicleKey`; `keys-delegates.js` exercises it) and a verifier without the registration record resolves it from the chain; D21 (with the first two D16 items) — `revokeIdentity` is single-shot and `revokedAt` is frozen, `changeOwner` and the clean-up revocations revert on a revoked identity (revocation is terminal), and `DIDRevoked` carries `previousChange`. *Fixed 2026-10-06 (merge: K-3, K-4, K-15; steps marked `FIXED (K-n)`):* K-3 (D16 rest) — `changeOwner` on a born vehicle reverts "MOBIVID: use transferVehicleOwnership", so the VID II ownership history can no longer be bypassed (`controller.js`, `revocation.js`); K-4 — `registerVehicleBirth` requires an identity without DID history, so a manufacturer cannot take over a self-registered, owner-changed or revoked did:ethr (`creation.js`, `revocation.js`); K-15 (D16 rest) — an OWNER-role issuer may record lifecycle events only for a vehicle it currently owns (`claims.js`). *Still open:* `revokeAttribute` accepts a value different from the one set; the same attester can attest the same event repeatedly; `transferRegistryAuthority` emits no event; `nonce` is dead state; `updateVehicleKey` does not revoke the old key; odometer monotonicity is not enforced; a `DECOMMISSION` event does not set the revoked flag.
